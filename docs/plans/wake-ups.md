A meeting about to start, a Slack "Ayanda I need you right now" from someone who matters (e.g. Alex Meyer), anything an agent judges urgent. The agent picks the severity and which device(s) ring. ## 0. Fix first: the presence calendar is always empty
- **Cause:** `apps/desktop/src/main/presence/calendar.ts` `findList()` returns `[]` for any array. The key in use is a Composio Connect key, so `ConnectBackend.execute` (COMPOSIO_MULTI_EXECUTE_TOOL) replies `{data:{results:[{response:{successful, data:{items|value:[...]}}}]}}`; the walk stops at `results`, every read "succeeds" with 0 events. Proven on today's real Google and Outlook replies (0 found; REST shape 1). "fetch failed" in main.log (twice, right after starts) is a side issue.
- **Fix:** `unwrapComposio()` takes `results[0].response`, an inner `successful:false` is a logged failure; `findList` descends into arrays; log when a non-empty list keeps 0 events; retry a failed read after 1, 2, 5 min; red-first tests with Connect-shaped Google and Outlook fixtures. Only calendar.ts parses `backend.execute` output in main.
- **Status (29 Oct 2026): DONE in 0.2.95** (devices ff2eac4 + 3315e16). A second cause showed in the live proof: Connect saves a reply over a few thousand tokens to its sandbox (`data.remote_file_info`) and returns only `response.data_preview`, each event cut short (his Outlook week: 9,343 tokens). Fixed by asking only for the fields the note reads (Google `fields`, Outlook `select`) and re-reading a cut reply for 60 h. Any delta read must do the same. Real Connect reply shape, confirmed live: `{successful, data:{results:[{response:{successful, data}, tool_slug, index}], total_count, success_count, error_count}, error, log_id}`; a failure comes back as `Error: {...}` with `response.successful:false` and the API error text in `response.error`.
- **Delta reads for wake-ups (checked 29 Oct 2026 against docs.composio.dev/toolkits/{googlecalendar,outlook}.md):**
  - Google: `GOOGLECALENDAR_EVENTS_LIST` accepts `syncToken`, `pageToken`, `updatedMin`, `showDeleted`, `singleEvents`, `fields`. `syncToken` cannot be combined with `timeMin`, `timeMax`, `orderBy`, `q`, `iCalUID`, `updatedMin` (the tool strips them, its description says). `nextSyncToken` arrives inside `data` on the last page only (ask for it via `fields`, e.g. `items(id,status,summary,start,end,updated,attendees,hangoutLink),nextPageToken,nextSyncToken`). A 410 means the token expired: full read again. Deletions show as `status:"cancelled"` items. `GOOGLECALENDAR_SYNC_EVENTS` is deprecated in favour of EVENTS_LIST.
  - Outlook: **no `lastModifiedDateTime` filter** on the read tools. `OUTLOOK_GET_CALENDAR_VIEW` takes only `start_datetime`, `end_datetime`, `timezone`, `top`, `skip`, `select`, `orderby`, `page_token`, `calendar_id`, `user_id`; `OUTLOOK_LIST_EVENTS` has `filter`, but its filterable list is start/end, subject, categories, importance, sensitivity, isAllDay, isCancelled, isReminderOn, type. Use **`OUTLOOK_LIST_CALENDAR_VIEW_DELTA`** instead: the first call with `start_datetime`/`end_datetime`, page with `skiptoken`, keep the `@odata.deltaLink` token and pass it as `deltatoken` (full link or bare token accepted) to get only added, changed and deleted events (`@removed`).
  - Webhook triggers exist (`OUTLOOK_EVENT_CHANGE_TRIGGER`, `GOOGLECALENDAR_*_WATCH`) but put Composio in the push path: out under the 18 Oct rule. Delta reads on our own schedule only.

## How it works
1. **The trigger: tool `wake_me`** for every agent, helper, desk and routine (main app and headless node): `wake_me({severity: critical|urgent|heads_up, title, what_to_do, source: {kind: meeting|slack|mail|routine|agent|..., ref, link}, devices?: auto|here|all, dedupe_key?, at?})`. `at` schedules it (meetings); no `at` fires now. It writes a synced `wakeup` row (devices replication, HLC) with state `pending | ringing | snoozed | acked | withdrawn`, and an internal event `wakeup.fired` / `wakeup.acked` into the workers' event store so routines can react (a desk follows up once he acked). Agents can fire and withdraw a not-yet-ringing wake; **no agent tool can ack or silence a ringing one.** Same `dedupe_key` within 10 min merges into the existing wake (no double ring); per-source rate limit with a log line.
2. **Severity (agent judges, the app enforces):** `critical` red (`--err`): every device at once, through DND and quiet hours. `urgent` amber (`--tert`): the device he is at, the other joins after 60 s without an ack; through DND. `heads_up` green (`--ok`): the device he is at, one ring cycle per minute; respects quiet hours. The tool description and a skill brief give the judgement rules: explicit "need you now" from a person he works for, a meeting starting, a live outage = urgent or critical; FYI never wakes him. Who counts is read from memory and connections, never hard-coded. Every wake is listed in a "Wake-ups" log he can see, with why and who fired it, so a bad call gets corrected (prompt rule or desk brief).
3. **Which device ("where he is"):** the presence data already built (`presence/presence.ts`): origin of his last message, PC window focus and OS idle, plus the phone's facts over the link (screen on, unlocked, app in front). Auto = the device with the freshest activity; unknown = all.
4. **Built-in sources.** *Meetings:* the fixed calendar service plans a wake per meeting per lead time (default 15, 5, 0 min; severity urgent at 0) with `at` and `dedupe_key = event id|lead`; skips cancelled, declined, all-day, and meetings he is already in (presence, PC mic in use by a meeting app, phone in a call). Changes: the phone's own calendar trigger (`triggers/Wakes.kt` `Calendar.watch`) and on the PC a small delta read (Google `syncToken`, Outlook last-modified) plus a confirm read 20 min before; a cancelled meeting withdraws its pending wakes. *Slack and mail desks:* their briefs get one line: call `wake_me` when a message needs him now, with the sender and the exact ask as `what_to_do` and the thread link as `source.link`. *Anything else:* any routine or agent.
5. **Reaching the phone in the background.** The chat link pauses 30 s after the app leaves the screen (`RemoteSession.onBackground`), and FCM is out (18 Oct rule: no third party in the path, and no Firebase in the app). So: (a) scheduled wakes (meetings) are synced ahead and armed locally with `ExactAlarms.set(..., clock = true)` (setAlarmClock fires in Doze, locked, app swiped away); (b) instant wakes use a new **wake channel**: a tiny WebSocket held by the existing specialUse foreground service (`system/WorkService`) that carries only `wakeup.*` events, heartbeat every ~4 min, a few KB an hour. A battery-unrestricted app keeps network in Doze, so it arrives in seconds. It connects to every reachable brain (PC, or the always-on server node as relay when the PC is off). The phone answers `wakeup.delivered`; no delivery within 30 s makes the sender ring every other device and note "phone not reached".
6. **Phone ring.** `WakeUpService` (foreground, mediaPlayback) loops the alarm sound on `AudioAttributes.USAGE_ALARM`, raises STREAM_ALARM volume for the ring and restores it after, vibrates continuously, holds a wake lock. Shows: (a) a `CATEGORY_ALARM` notification on a channel with `setBypassDnd(true)` and a full-screen intent to `WakeUpActivity` (`showWhenLocked`, `turnScreenOn`), which covers the lock screen; (b) when the phone is unlocked and in use (a full-screen intent then only shows as a banner), an overlay window `TYPE_APPLICATION_OVERLAY` over every app, then the activity (holding "Appear on top" also lets it start from the background). Screen: the severity colour edge to edge, title, the exact `what_to_do`, source and time, buttons **I'm on it** (ack), **Snooze 5** (re-rings, same severity), **Open** (join link or Slack thread). No timeout. Named `WakeUp*` so it does not clash with the existing agent `Wakes`.
7. **PC ring.** A frameless always-on-top full-screen window on every display, same colour, text and buttons, looping sound at the app's full volume, taskbar flash. It cannot wake a sleeping PC; the phone covers that.
8. **Acknowledge.** Writes `acked` (or `snoozed` with a new `at`) to the row and sends `wakeup.ack` on the link and the wake channel; the other devices stop within seconds, or at their next sync if offline. The ack goes back to the source (the desk sees `wakeup.acked`).
9. **Settings > Wake-ups** (synced): on/off; meetings source on/off, lead times, which calendars; snooze length; quiet hours (critical and urgent ignore them); ring on phone / PC; a "Test a wake-up" button per severity; the permission checklist below with a fix-it button per row.

## Pause and idle on a computer (30 Oct 2026, 0.2.113)

He goes home for the weekend and the PC must not beep in an empty room; the phone keeps ringing.

- Settings, per machine (not in the shared bundle): `wakeupsRingHere`, `wakeupsPauseHereUntil` (ISO, '' none; both free for settings_set), `wakeupsPhoneOnlyWhenIdle` (default on), `wakeupsIdleMinutes` (default 5; both read-only to agents, like snooze, quiet hours and volume).
- `shared/wakeups.ts decideHere`: a computer that is paused, idle or locked holds back. It writes a row `<wake>:away:<device>`, which takes it out of the wake's targets (`effectiveTargets`), so the wake is for the other devices at once. The phone reads only `targets` and `seen` in its snapshot, so it needs no change.
- Never unheard: no phone linked, rings here at once; no phone says `seen` within 30 s, rings here then. Only a phone's or tablet's `seen` counts, because another computer may be in the same empty room. A `seen` from before a snooze is not proof of the next ring; the snapshot leaves it out, so the phone says it again.
- Off is off: with Ring on this computer off, no new ring starts, not even as the last resort.
- A ring in progress is never silenced: going idle, a pause and the switch going off (by an agent too) only stop new rings. This is what lets agents set these two keys while no agent can silence a wake. A ring in progress survives a restart (`seen` for this ring).
- He comes back to an active computer while a wake rings: it joins (a 5 s poll runs only while a wake rings elsewhere; lock, unlock and resume also look at once). The phone keeps ringing: a computer that came back does not return to the targets.
- His own test button rings where he asked, paused or not.
- Log: `hereNotes`, "not ringing here: paused until Mon 2 Nov 08:00", "not ringing here: PC idle", "rang here: no phone confirmed in 30 s", "joined here: he came back". Shown in Settings > Wake-ups and wake_list; also in main.log.
- Proof copies: `AGENT_WAKEUP_PROOF_IDLE=<file>` (only with `AGENT_WAKEUP_PROOF=1`) holds active, idle or locked in place of the real state.
- A server on an older version sends the phone the raw targets: a wake targeted at a paused computer then reaches the phone at 30 s, the same moment this computer falls back. It stays safe, but deploy the server with the same version.
