# Plan: custom mini-apps made on demand

Asked by Ayanda, Thu 29 Oct 2026 10:50 (dictated as "Job applications"). Planning only, nothing built.

## Goal
When he asks ("a calendar across all my accounts", "a dashboard of X", "a tracker for this plan I follow"), an agent makes a small app, saves it, and he opens it from the **Apps** page; the few he uses most he **pins to the sidebar** (rail), the rest stay on the Apps page. Works on the PC and the phone. A calendar view is a mini-app, never a built-in view (Ayanda, 29 Oct 11:04). He edits it later by asking. It looks exactly like the Agent app in light and dark, reads data only through the app's own tools with permissions, and cannot touch anything it was not granted. Generic product: no app is pre-built for his accounts.

## Cordis verdict
Cordis is real: `cordis` (cordiverse, MIT, ~9.5k stars, npm 4.0.0-rc.12, readme says "API is not yet stable") and DeepSeek's fork `@deepseek-ai/cordis` 4.0.5 (MIT) inside DeepSeek Harness (early open-source release, Aug 2026). It is an in-process TypeScript plugin kernel: Context, plugins, services with `inject`, effects undone when a plugin unloads, events, hot reload. It has **no sandbox** (plugins run with full Node rights), targets Node only (no Android; the JVM port cordis4j is a third-party project), and has nothing for UI isolation or theming.
**Use it for what it is good at, not as the sandbox:** the trusted host side in the Electron main process and the headless node. Each mini-app is a Cordis plugin built by host code from the app's manifest (never from agent-written code), so its bridge handlers, data subscriptions and schedules are effects that vanish on unload; edit = reload, delete = everything gone. Host services (`calendar`, `tools`, `storage`, `theme`) are Cordis services the plugins `inject`. Pin one version behind our own small `PluginHost` interface so it can be swapped. Agent-written code runs only in the sandboxed frame below.

## How it works
1. **What an app is:** a folder `<userData>/miniapps/<id>/` with `manifest.json` (name, icon, description, `permissions`: tool names with read or write, connected accounts by rule, network none, `refresh`: on open, on an event, or a routine), `index.html` + `app.js` (or a plain OpenUI document for simple dashboards), and a per-app key-value store. Stored as a synced row (`miniapp` entity, files inline, size cap 1 MB) so every device has it; each save is a version (same history model as memory), so "undo the last change" works.
2. **Sandbox (desktop):** opened in the main sheet as an `<iframe sandbox="allow-scripts">` (no `allow-same-origin`, so no cookies, storage or parent access) loading `miniapp://<id>/` from a custom protocol the main process serves with a strict CSP (`default-src 'self'; connect-src 'none'; img-src 'self' data:`). No network, no Node, no `window.agent`. Only door out: a `MessageChannel` port.
3. **Bridge:** a tiny `agent.js` injected into every app: `agent.call(tool, args)`, `agent.subscribe(topic, fn)` (e.g. `tasks.changed`, a worker event), `agent.store.get/set`, `agent.theme` (current tokens + `onChange`), `agent.ask(question)` (hands to his agent). The host plugin checks each call against the manifest, then runs it through the SAME tool executor, account rules and approval cards as agents do. Reads allowed by the manifest run; writes ask first unless he ticked "let this app do X". Rate limit per app. Granting a new permission is shown to him once.
4. **Design tokens:** the source is `apps/desktop/src/renderer/styles/tokens.css` (`--bg`, `--on-bg`, `--primary`, `--pc`, surfaces `--s-*`, `--outline*`, `--ok`, `--err`, `--font`, radii `--r-sm..--r-xl`, motion curves), with light, dark-by-system and `[data-theme]` blocks; accents in `src/shared/brand.ts` (`ACCENTS`, `brandLook()`, already used to theme the guide overlay); the choice applied by `renderer/state/theme.ts` (`applyTheme`, `applyAccent`); the phone mirrors it in `ui/theme/Theme.kt`. Build step: parse tokens.css once into `shared/tokens.json` (one source). The host serves `miniapp://<id>/_agent/tokens.css` (all vars for both themes + the live accent) and `ui.css`, a small kit of native-looking parts (card, button, chip, table, list, tabs, empty state, chart colours) written only with those vars and the app's spacing scale. The frame's `<html data-theme>` follows the app: the renderer posts `theme` on every `applyTheme`/`applyAccent` and on `nativeTheme` change, so a switch is instant.
5. **Making and editing:** new agent tools `miniapp_create`, `miniapp_update` (whole files or a patch), `miniapp_list`, `miniapp_open`, `miniapp_delete` (asks). A built-in skill brief tells agents: use `ui.css` parts, only `var(--...)` colours, test both themes. Save is refused when a lint finds hard-coded colours, fonts or radii outside `var()`, external URLs, or calls not in the manifest. Before telling him it is ready, the host renders it offscreen at 1440 and 390 in light and dark and the agent looks at the four shots.
6. **Apps page and pinning to the sidebar (first-class).**
   - *Apps page:* a new rail nav entry "Apps" (beside Routines and Connections in `renderer/shell/Rail.tsx` `NAV`): a grid of every app with icon, name, one-line description, last opened, a pin toggle, and Open / Edit by asking / History / Delete.
   - *Pin / unpin:* from the Apps page, the app's own title bar, a right-click on its rail icon, or by asking (`miniapp_pin {id, position?}`, `miniapp_unpin {id}`). Pinned apps get their own rail section between the nav and Projects, each a rail item with the app's icon and name (label hidden when the rail is collapsed, tooltip shown), active state like other rail items.
   - *Order:* drag to reorder in the rail or on the Apps page; the agent can set `position`. Stored as an ordered list `pinnedApps: [id]` in the synced settings, per profile, so every device shows the same order.
   - *Icon:* each app has `icon` in its manifest: either a name from the app's own icon set (`IconName`, so it matches the nav) or a small agent-drawn SVG that uses only `currentColor` (lint refuses any fill or stroke colour), so it takes the rail's colours in light, dark and every accent. He can change it by asking or from a picker on the Apps page.
   - *Room:* the 0.2.79 rule holds: nav, Settings and account never shrink. Pinned apps shrink like project tiles; ones that do not fit go into a "+N" entry that opens the Apps page. Cap 8 pinned (setting).
   - *Phone:* pinned apps appear in the phone's navigation in the same order; long-press offers an Android home-screen shortcut (`ShortcutManager.requestPinShortcut`).
7. **Phone:** the same app in a WebView (JS on, file and content access off, no network via `shouldInterceptRequest`), tokens from Theme.kt in the same CSS var names, and a `@JavascriptInterface` bridge that forwards `agent.call` over the existing RPC (`miniapps.call`) to a brain; only when open, so no background data use.
8. **Reuse, not rebuild:** OpenUI (`renderer/openui/`) renders "simple" apps declared as openui-lang with data bindings, no JS at all; learned apps and Composio actions are just tools an app may be granted; workers and routines provide refresh events (`agent.subscribe`). The calendar service from wake-ups.md (step 0 fix) is a host service: it feeds tasks, routines and wake-ups, and a **calendar mini-app** reads it through `agent.call('calendar_events', {from, to})` with a read grant (every connected calendar in one view, `calendar.changed` subscription).

5. First apps end to end: a calendar across every connected calendar (needs the calendar fix in wake-ups.md), a tracker for a plan he follows (reads and ticks tasks), and a dashboard (counts from tasks, routines and a worker's events).

## Risks and open questions
- Cordis is pre-1.0 in spirit ("API not yet stable"); hence the wrapper and a pinned version. If bundling it into Electron main fights us, the wrapper falls back to a 100-line registry with the same dispose model.
- A bad app can still mislead (show wrong numbers) but cannot exfiltrate: no network, all data via audited tool calls.
- Size and sync cost of apps on mobile data: inline files capped, assets as data URLs only.
- Open: do apps live per profile (Personal-, Acme...) or once for all? Proposed: per profile, so data rules follow the profile.

## Test plan
- Unit: manifest checks (denied tool, write without grant asks, rate limit), lint rules, token parse (every var present in both themes), version history and undo.
- Security: an app that tries `fetch`, `top.location`, `document.cookie`, `window.parent`, a form post, a remote `<img>` and a tool outside its manifest: all must fail, logged.
- Theme: switch light, dark, system and every accent while the app is open; screenshot diff of `ui.css` parts against the app's own components at 1440 and 390.
- Pinning: pin, unpin, reorder by drag and by asking, change icon; collapsed and expanded rail; shrink the window height (nav never shrinks, pinned apps go to "+N"); the order matches on a second device and the phone; a pinned app that is deleted leaves the rail.
- End to end in a test copy (own temp user-data dir, `AGENT_FAKE_CALENDAR`): ask "make me a calendar of all my accounts", pin it, open it from the rail, edit it by asking ("show only this week"), undo; ask for a plan tracker (stays on the Apps page), tick an item (write asks the first time); then a dashboard; delete one; same apps and pins on the phone. ## Built (29 Oct 2026, desktop 0.2.97 + phone 0.15.2)
- **Data:** `miniapp` rows (packages/core ipc.ts MiniAppRow): files inline, permissions, subscribe, refreshMinutes, version + last 10 versions, `pinned` order number on the row (so every device shows the same order), `allowed` (only he sets it, in the window), `data` (agent.store), `check`. `miniappPinCap` setting (8). Per profile: an app keeps the profile of the agent that made it; its calls run with that profile's accounts.
- **Lint and kit:** shared/miniapps.ts (lint, grantable tools, checkCall, topics, icon parse, versions, pins), shared/miniapp-kit.ts (CSP, ui.css, agent.js, serveMiniApp), shared/miniapp-tokens.ts generated from tokens.css by scripts/gen-miniapp-tokens.mjs (test keeps them equal).
- **Host side:** main/miniapps/plugin-host.ts: `PluginHost` wrapper, Cordis engine (@deepseek-ai/cordis 4.0.5, exact pin, bundled into main) and a plain engine with the same dispose model. Cordis worked in Electron main, the headless bundle and vitest: kept. host.ts: one plugin per app, sessions/subscriptions/refresh timers are its effects. store.ts, protocol.ts (miniapp://<id>/, CSP, window guard), check.ts (offscreen look check, preload/miniapp-check.ts), ipc.ts (IPC + RPC miniapps.session/call/close/list/serve/pin/unpin, event miniapps.push).
- **Tools:** miniapp_guide/create/update/get/list/open/pin/unpin/undo/check/delete (delete asks), calendar_events (presence calendar cache, range + onChange), task_list format json + include_done.
- **Window:** Apps nav entry, Apps page (views/MiniApps.tsx), open app (views/MiniAppView.tsx, iframe sandbox allow-scripts + MessagePort), pinned section (shell/PinnedApps.tsx, lib/miniapps.ts fitPinned), renderer CSP frame-src miniapp:.
- **Phone:** com.past9.phoneaos.miniapps (MiniApps.kt hub + rules, MiniAppScreens.kt): Home row of pinned apps in the sidebar order + All apps, Apps screen with pin and home-screen shortcut (ShortcutManagerCompat), locked-down WebView (virtual host https://<id>.miniapp.invalid, every other request 403, navigation refused, no file/content/storage), bridge over RPC to the computer. Device feed: a phone hears only {entity:'miniapp', id} (never the files).
- **Not done:** the headless node serves no mini-app sessions (the phone runs apps through the computer); agent.store writes re-sync the whole row (split `data` into its own entity if apps grow); a pinned app's offscreen look check runs only on a desktop.
