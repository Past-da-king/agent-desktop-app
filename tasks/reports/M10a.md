# M10a report: helpers (main process only)

Status: done. `bash scripts/gate.sh M10a` prints `GATE M10a PASSED` (175 tests, 12 in `*helpers*`).

## What I built

- `apps/desktop/src/main/runtime/helpers.ts`: `HelperManager`, ported from `startHelper`, `runHelper`,
  `steerHelper`, `pushHelper`, `stopHelper`, `helpersReport` and the result note in
  `reference/phone/AgentRuntime.kt`.
  - Each helper runs its own `AgentLoop` with the HELPER system prompt, the worker toolset, and its
    own transcript under `thread = <helper id>`.
  - Four run at once; the rest queue. States are `working`, `done`, `failed`, `stopped`. A queued
    helper is `working` with `queued: true` in its meta.
  - A steering inbox is read before the helper's next step.
  - Finished results go back to the main agent as a new main turn:
    `[Helper #<id> "<label>" finished]\n<result>` (or `failed`). The give-up regex adds the
    `helper_push` nudge, and stops nudging after two pushes. A `together` batch is held until every
    helper in it is done and then delivered as one packed message.
  - `kind: 'helper'` chat rows carry `{id,label,state,summary,startedAt,endedAt,model,result,pushes,queued}`.
    Its tool rows are `kind: 'activity'` with `helper` and `by`, so M10b can expand a card into them.
  - Startup repair marks helpers left `working` as failed ("Interrupted when the app closed.").
- `apps/desktop/src/main/tools/helpers.ts`: `delegate(tasks:[{label,brief,model?}], together?)`,
  `helper_steer(id, message)`, `helper_push(id, message)`, `helpers_status()`, `helper_stop(id)`.
  Registered by one line in `runtime/toolset.ts`.
- `apps/desktop/src/main/runtime/budget.ts`: `StepBudget` and `budgeted`, ported from `Budgeted`.
  The main agent's action tools stop after 5 calls in a turn with the reference's step-limit message.
  The budget is reset when the person sends a message, not when a helper result comes back.
- `runtime/toolset.ts`: `buildWorkerToolset` (no helper tools, no budget) and `buildToolset`
  (worker tools + helper tools, then every non-main-owned tool wrapped in the budget). Later
  milestones should append their groups to `buildWorkerToolset`; anything not in `MAIN_OWN_TOOLS`
  is automatically budgeted.
- `runtime/prompt.ts`: MAIN gains the YOUR JOB helper rules and a YOUR HELPERS section naming the
  single roster model; HELPER gets its own work rules and the "reply with ONLY the result" tail.
- `runtime/runner.ts`: `deliver(text)` starts a new main turn with a helper result (or joins the
  active run as a steering note), helper cards are routed to the manager in `answer`/`decide`, and
  `restore()` also repairs helper rows.
- `apps/desktop/src/main/index.ts`: builds the worker toolset, the manager, the shared budget and
  the main toolset, and gives the manager a delivery callback into the Runner.
- `apps/desktop/test/helpers.test.ts`: 12 tests with the real fake AI server (no mocked fetch):
  delegate through the main agent and delivery as a main turn, parallel helpers (a real barrier),
  steer before the next step, stop, queue beyond four (observed peak 4), give-up nudge, push keeping
  the helper's conversation, batched `together` results, status report, restore, toolset separation,
  and the main action budget through six real `web_fetch` calls to a local server.

## Deviations and choices

- Helper ids are chat row cids (UUID strings), not Kotlin `Long`s, because every row in this app is
  identified by a cid. The tools take `id` as a string.
- `helper_steer` has no `restart` flag: the M10a tool list specifies `(id, message)`. Steering a
  finished helper falls through to `helper_push`, which carries its conversation on.
- `delegate` accepts `model` because the M10 brief includes it, but v1 has a one-model roster: a
  requested model that is not the user's chosen model falls back to that model, as the Kotlin does
  when its roster has one entry.
- The worker toolset here is core + memory + tasks, because files, shell, code, browser and routines
  live in other milestones. `buildWorkerToolset` is the single seam those groups should be added to.
- Helper `ask_user` / `request_approval` create cards tagged with `helper` and are waited on by the
  manager. `Runner.answer` / `Runner.decide` route those to the manager, so a helper cannot deadlock
  on a card the UI does show.
- The reference's note says `finished` for a completed run even when the text is a give-up; I kept
  that. The give-up regex still adds the push nudge.

## Not in this milestone

- The renderer half of M10 (helper cards, expanding a helper's activity, hiding finished ones, Home
  "Right now", palette "Stop all helpers", mock demo cards) is M10b.
- No IPC/preload/`AgentApi` additions were made for helpers yet; the contract is unchanged here.
  M10b will need to add them additively, and the mock bridge.
- `delegate`'s `restart`-style steering, multi-model rosters and subscription helpers are out of v1.

## For the next milestone

- `HelperManager` already exposes `live()`, `stopAll()`, `stop()`, `status()` and the chat rows M10b
  needs. Use `meta.helper` to find a helper's activity rows.
- A helper's `kind: 'helper'` row is created before it starts, so the UI can show a queued card at
  once. `meta.summary` is the live "now" line; `meta.state` is the state.
- Finished helper cards should be hidden once the main reply has landed, as on the phone. The result
  is in the main turn, and `meta.result` keeps the last 6000 characters for the card.
