# M2 report: Core sync

## Built

- `packages/core/src/sync/hlc.ts`: `HlcStamp`, `encodeStamp`, `decodeStamp`, `compareStamps` and `Hlc(device, clock)`.
  The compare order is numeric millis, numeric counter, then device string. `now()` moves strictly forward and
  `observe()` follows the Kotlin rules for a remote stamp that shares the same millisecond.
- `packages/core/src/sync/change.ts`: the `Change` wire type, re-using `EntityName` from `ipc.ts`, plus
  `changeFromJson` / `changeToJson` so unknown server rows are skipped rather than crashing a pull.
- `packages/core/src/sync/store.ts`: the `SyncStore` interface with `deviceId`, `localChanges`, `applyRemote`,
  `pushMark` / `setPushMark` and `cursor` / `setCursor`, all async.
- `packages/core/src/sync/client.ts`: `SyncClient(baseUrl, token, fetchImpl?, allowHttp?)`, `push`, `pull` with
  `{wait, signal}`, static `register` / `login`, and `SyncException(status, message)` where status 0 means the request
  never reached the service. It sends `Authorization: Bearer`, parses `{error:{message}}`, caps the long poll at 55 s
  and sends the Kotlin user agent.
- `packages/core/src/sync/engine.ts`: the push-then-pull engine with a serialising mutex, `syncOnce()`, a background
  `start()` / `stop()` long-poll loop (25 s), exponential backoff from 2 s to 60 s, a 300 ms debounced `nudge()`,
  `onStatus` listeners carrying the `ipc.ts` `SyncStatus` shape, `onApplied(changes)` and `markSignedIn`.
- `packages/core/src/sync/memory-store.ts`: `MemorySyncStore`, a complete in-memory store with last-writer-wins apply,
  own-echo skipping, local row helpers `put` / `remove` / `get`, and persisted push mark and cursor.
- `index.ts` re-exports all six modules.

## Deviations and decisions

- `SyncClient` takes `allowHttp` as a fourth constructor argument, and the static `register` / `login` take it as a
  fifth argument after `fetchImpl`. This keeps the milestone's requested third `fetchImpl` parameter while still
  reusing `http-policy.ts`.
- `MemorySyncStore` records whether a row was written locally. Without that, a row applied from another device would
  be returned by `localChanges` on the next pass and pushed back to the server. The real database store in M3 needs the
  same distinction (a dirty/local flag, or an equivalent) rather than relying only on the push mark.
- A nudge aborts the in-flight long poll (never the loop) so a local write is pushed in about 300 ms instead of waiting
  for the 25 s poll to expire. A restarted loop is guarded by its own `AbortController` identity, so an old loop cannot
  run passes after `start()` is called again.
- Changes without a `seq` omit it on push. The fake and Kotlin servers ignore the field on input.

## Notes for M3

- `db.ts` should implement `SyncStore`: keep `device_id`, `push_mark` and `cursor` in `kv`; store a local/dirty flag
  per row so rows applied from the server are not pushed back; skip a remote stamp whose device equals `deviceId`
  before calling `hlc.observe`; and compare the existing row stamp against the remote stamp before overwriting.
- Call `engine.nudge()` after every local write, `engine.start()` after a successful sign-in and `engine.stop()` on
  sign-out. Use `engine.syncOnce()` for the onboarding first-sync step.
- The engine's client factory should return `null` while signed out; that makes a pass a no-op with `signedIn: false`.
- The fake server keeps accounts in memory. The offline test restarts it on the same port and registers the same email
  again to obtain a fresh token, so do not assume a token survives a server restart in tests.
- No new dependencies were added.
