# M4 report: renderer foundation

## What was built

- Split the mockup stylesheet into `tokens.css`, `base.css`, `onboarding.css`, `shell.css`, `views.css` and
  `responsive.css`, imported by `styles/index.css`. The mockup's class names, tokens and spacing are kept.
- Roboto and Roboto Flex are loaded from Google Fonts in `index.html`; the CSP now allows the two font hosts.
- UI primitives: `Icon` (all the mockup paths), `Mascot` (all nine ids, busy morph, spin, eyes, size), `Wave`,
  `Ring`, `Button`, `Field`, `Segmented`, `Switch`, `Chip`, `Eyebrow`, `SectionHeader`, `Skeleton`, `EmptyState`,
  `Dialog` (focus trap, Escape, focus return), plus small `Pill`, `Kbd`, `Avatar` and `IconButton` helpers.
- State: `useSettings` (load, save, subscription, theme and accent applied everywhere), `useData` (typed per-entity
  lists, loading and loaded flags, subscription to `data.onChanged`), `useUi` (hash route, selections, filters,
  overlay, rail state), `theme.ts` (all eight accents, light/dark/system), and the `useRoute` hook.
- Shell: real `TitleBar` controls through `window.agent.window`, command bar, live sync pill, theme toggle, `Rail`
  with agent card, New chat, navigation and needs badge, recent chats, Settings and account, `Sheet`, chat `Panel`,
  `Palette` and `QuickAsk`, plus the phone navigation bar.
- Views: Home, Chat, Tasks, Memory, Routines, Connections and Settings, including every `ChatItem.kind` the
  contract defines (user, agent, activity, helper, question, approval, notice, report), markdown-lite for agent
  text, memory search/filter/detail with real `[[links]]` and the pure-SVG link graph, routine and to-do toggles,
  approve/decline and answer chips, dialogs for adding and editing, and empty/loading states.
- Onboarding: the four steps as working, validated screens on the mock bridge (sign in/create account, sync
  progress, AI provider and key check, name/colour/mascot and Open Agent), with the phone QR and subscription
  rows disabled with "Coming soon".
- Bridge: `bridge/seed.ts` holds the demo persona and the demo, empty and big datasets. `bridge/mock.ts` is a full
  in-memory `AgentApi`: four modes read once from the query, CRUD that fires `onChanged`, chat echo with an
  activity chip, settings persisted in `localStorage` behind try/catch, and the four mock behaviours the milestone
  lists. `bridge/local-chat.ts` gives Electron the same chat echo through the real local store until M6.
- Boot logic routes a fresh install to onboarding and an onboarded install to the requested hash, the last view or
  Home. Keyboard: Ctrl/Cmd+K, Ctrl/Cmd+N, Ctrl/Cmd+, Escape, and Ctrl+Shift+Space in the browser.

## Known differences from the mockup

1. Text smaller than 12px was raised to satisfy the repo rule: `kbd` 11px to 12px, the hero phone/desktop labels
   9px to an 11px uppercase eyebrow, the embedded browser labels 10px and 11px to 12px, and the collapsed-rail
   badge 11px to 12px. Spacing and layout are otherwise the mockup's.
2. The "Sign in with your phone" QR is a disabled card with a phone icon and "Coming soon", not a fake QR, as
   PLAN.md section 11 requires.
3. Subscription rows on the AI step are visible but disabled with "Coming soon", as section 11 requires.
4. The onboarding provider chips show six common providers (Anthropic, OpenAI, Google Gemini, DeepSeek,
   OpenRouter, Other) so the Check key button stays on a 1440x900 screen. All eight providers are in the contract
   and in the catalog; M5 should call `settings.providers()` and show every one.
5. Settings shows Light and Dark only, like the mockup. The `system` preference is supported by the settings model
   and resolves to the OS theme; there is no third System button in the segmented control.
6. Settings' AI "Change" button is disabled "Coming soon". Editing the provider, model and key outside onboarding
   arrives with M5 and the live settings work.
7. Routines' "Run it now" is disabled "Coming soon". The mock implements it, but the real scheduler is M7.
8. Helpers are hidden in the chat panel until M10, as section 11 requires. A `helper` chat item still renders in
   the thread if data contains one.
9. The chat panel's browser is a placeholder ("The agent's browser opens here when it needs one") and "Take over"
   is disabled until M9.
10. Connections is honest about what exists: This computer, notifications, the quick-ask shortcut and folder
    granting work; browser, drop zone, profiles, other machines and accounts are visible and disabled with
    "Coming soon". The mockup's named Home server and Build box are replaced by one "Another machine" row.
    Folder "Allow" is functional in the browser mock and disabled in Electron until the folder picker lands in M8.
11. Recent chats come from `chat_item` rows of kind `branch`, which carry title, device, time and active metadata.
    There is no conversation entity yet, so this is the best available shape; Chat falls back to the first user
    message when no branch row exists.
12. `MemoryKind` has no "company" value. The demo's Acme page is a Fact, and Memory filters show the contract's
    real kinds (Person, Fact, Preference, Decision, How-to, Event, Skill) rather than the mockup's Person/Company/
    Preference set.
13. Memory has no "used in N chats" field, so the detail card says that the agent uses the edited page from now on
    instead of claiming chat counts. The link graph shows up to five connected pages, laid out like the mockup;
    any further links are still listed as chips.
14. There is no surname field, so the account row shows the user's chosen name and email; the mockup's
    "Sam Dlamini" is seeded as "Sam".
15. Tasks have no per-task agent note field, so the detail card uses one honest sentence about checking before
    anything leaves the computer instead of the mockup's task-specific sentence.
16. A chat has no title field yet; the header uses the active branch title, or the first user message shortened.
17. Demo data is close to the mockup but not byte-identical: goal progress is 1/3, the recent chats are ordered by
    their timestamps, unspecified due times are 09:00, and all dates are generated relative to today.
18. The mock seeds one harmless example attachment path (`brief.pdf`) and one example granted folder, so Attach
    and Allow do something visible in the browser preview. Data itself is in memory; only settings persist.
19. Until M6, Electron chat uses the local echo adapter in `bridge/local-chat.ts` and writes its rows through the
    real `data` API. The browser uses the mock bridge's own echo. M6 should replace `chat` in `bridge/index.ts`.
20. The palette's "Add a to-do" creates the mockup's "Call the dentist" row for real, then opens Tasks with it
    selected. The mockup's inert "New page", "New routine", "Add to-do" and "Edit page" actions became working
    dialogs or real inserts.
21. Window controls are real in Electron and no-ops in the plain browser preview, where there is no window to
    control.

## For the next milestone

- Renderer imports of `@agent/core` are aliased to `packages/core/src/browser.ts` in both Vite configs. That file
  exports only the IPC contract and the provider catalog, because the barrel also exports Node-side runtime code.
  Any new value the renderer needs from core must be exported there too.
- `bridge/index.ts` exports `agent` (real bridge or mock) and `chat` (mock/echo until M6). Views talk to `chat` for
  send/stop/state/answer/decide/onEvents; M6 should switch that export to the real runner without touching the
  views.
- The onboarding step is in the hash but is not persisted across a reload yet. M5 must keep it in settings or
  sessionStorage, wire Advanced/sync errors, add the model field and render every provider from
  `settings.providers()`, and give sync a Retry plus Skip path.
- Question cards marked `context: "home"` are hidden in the chat thread by the seed only so the Home question does
  not also appear in the thread. Real runner cards have no such marker and render in both places.
- The untracked `logs-orchestrator.out` at the repo root was present during this milestone and was deliberately
  not committed.
