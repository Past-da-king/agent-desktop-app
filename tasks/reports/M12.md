# M12: Windows-native correctness and the environment scan

## What was built
- `runtime/environment.ts`: a dependency-injected `resolveCommand` (PATHEXT order, `.PS1` added when
  the machine's PATHEXT leaves it out, case-insensitive Windows lookup through a directory listing,
  directories and zero-byte WindowsApps aliases skipped, exec bit honoured elsewhere) and
  `scanEnvironment` for shells, runtimes (Node, Python via `py -3` / `python` / `python3`, Git) and AI
  tools (Claude Code, OpenCode, Gemini CLI, Codex, Antigravity, with install folders built only from
  `LOCALAPPDATA`, `APPDATA`, `HOME`, `USERPROFILE`). Versions run `<tool> --version` in parallel with
  a 4 second timeout; nothing else is ever executed. WSL is a note on Windows, never a shell.
  `createEnvironment` caches for the session and rescans on `{ refresh: true }`.
- `runtime/environment-host.ts`: the real fs probe and version runner, routed through the spawn helper
  so `.cmd` shims are version-checked through `cmd.exe` and `.ps1` through PowerShell.
- `runtime/spawn.ts`: `spawnResolved` (`.exe` direct, `.cmd`/`.bat` through `cmd.exe /d /s /c`,
  `.ps1` through `powershell.exe -NoProfile -ExecutionPolicy Bypass -File`), plus testable quoting.
- `runtime/paths.ts`: Windows canonicalisation (mixed slashes, drive and UNC paths, `\\?\` prefixes,
  trailing dots/spaces, reserved device names, alternate data streams, raw device paths).
- IPC `environment.scan(refresh?)` added to the contract, preload, main handler and mock bridge
  (mock reports a Windows machine with PowerShell 5.1, Node, Python, Git, Claude Code and OpenCode
  found, Gemini CLI not found).
- Connections has a "FOUND HERE" card with Shells / Runtimes / AI tools, found markers, versions and
  "Scan again". Settings has the compact summary and the same button.
- The system prompt gains a `THIS COMPUTER` block: OS, the shell `shell_run` uses, found runtimes and
  AI tools by name and version (no paths), and the rule never to suggest installing anything unasked.
- `shell_run` chooses its shell from the scan (pwsh, then Windows PowerShell with UTF-8 wrappers, then
  cmd with `chcp 65001`), accepts `powershell`/`cmd`/`bash` only when found, shows the shell on the
  approval card, and kills the whole tree with `taskkill /PID <pid> /T /F` on Windows.
- `run_code` uses the scanned Node or the app's own runtime with `ELECTRON_RUN_AS_NODE=1`, and says
  plainly when Python is absent without attempting an install.
- `APP_ID` now drives `app.setAppUserModelId` (matching electron-builder's `app.agent.desktop`), the
  login item passes the packaged executable path, and the Windows tray icon is sized for display scaling.

## Tests
83 new tests across `environment.test.ts`, `spawn.test.ts`, `shell-platform.test.ts`,
`files-win32.test.ts` and `code-runtime.test.ts`. The suite is 536 tests, all green.

## What could not be tested on Linux
- Actually running `cmd.exe`, `powershell.exe`, `.cmd`/`.ps1` shims, `taskkill`, or `py -3`. The
  quoting and invocation shapes are unit tested with an injected `win32` platform and a capturing
  spawn, and the host tests prove argument round-trips through a real `.exe` and a POSIX script.
- Real Windows path semantics: 8.3 short names, junctions and symlinks are resolved by `realpath`
  on the real machine; the Windows tests use a case-insensitive virtual file system.
- Tray DPI rendering and toast attribution (app user model id) need the real Windows shell.
- A full scan against a real Windows PATH; the scan itself is exercised through injected file maps
  and a recording exec.
